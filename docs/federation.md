# Intent Commit Federation v1.3

Federation v1.3 extends the existing verifiable outbound model with **author-approved argument maps** while preserving compatibility with federation 1.0, 1.1, and 1.2 objects.

Intent Commit still does not implement remote inbox delivery, following, ActivityPub compatibility, or arbitrary remote URL fetching. The current goal is a stable trust and authorship model before inbound networking is added.

## Public object families

Federation now has four distinct object families:

```text
1. Federated utterance
   A human-approved COMMITTED statement with a canonical URI.

2. Lifecycle relation
   Signed retraction or revision of a federated utterance.

3. Provenance edge
   Signed cites / supports / challenges relation between two federated utterances.

4. Argument map
   Signed claim / reason / objection / qualification structure inside one federated utterance.
```

These are not interchangeable. A lifecycle event changes the author's later stance toward an old utterance. A provenance edge asserts a relation between public utterances. An argument map asserts how the author structures the content of one utterance.

## Consent boundary

Each widening or interpretation of public commitment requires a separate human action:

```text
Room COMMITTED
      ↓
Federation publication approval
      ↓
Signed public utterance
      ↓
Optional later approvals
      ├── retraction / revision
      ├── provenance edge
      └── argument map
```

Owners, moderators, other participants, and AI agents cannot perform these author-only actions for someone else.

## Instance identity

An enabled instance maintains a persistent Ed25519 key pair. By default:

```text
data/federation-private.pem
data/federation-public.pem
```

The private key is never exposed through HTTP. The public key, issuer, current federation version, supported historical versions, and endpoint templates are discoverable at:

```text
GET /.well-known/intent-commit
```

Production federation should use HTTPS and a stable `PUBLIC_BASE_URL`. The key pair is part of the long-lived instance identity and should be backed up securely.

## Version compatibility

The reference implementation verifies:

```text
1.0  signed utterances
1.1  signed retraction / revision
1.2  signed provenance edges
1.3  signed argument maps
```

New objects generated by the current implementation carry federation version `1.3`. The schemas for older object families accept the newer version while retaining their historical minimum version.

## Public endpoints

Instance descriptor:

```text
GET /.well-known/intent-commit
```

Signed utterance:

```text
GET /federation/utterances/:messageId
```

Relations and structure for an utterance:

```text
GET /federation/utterances/:messageId/relations
```

This response separates lifecycle relations, incoming/outgoing provenance, and the optional argument map.

Signed lifecycle event:

```text
GET /federation/events/:eventId
```

Signed provenance edge:

```text
GET /federation/provenance/:edgeId
```

Signed argument map:

```text
GET /federation/arguments/:mapId
```

Public graph:

```text
GET /federation/graph
```

The graph exposes federated utterance nodes, cross-utterance provenance edges, lifecycle summaries, and separately signed argument maps.

## Author publication APIs

Publish an already committed utterance:

```text
POST /api/rooms/:code/federation/publish
```

Retract:

```text
POST /api/rooms/:code/federation/retract
```

Revise:

```text
POST /api/rooms/:code/federation/revise
```

Create a provenance relation:

```text
POST /api/rooms/:code/federation/provenance
```

Privately request an argument-structure suggestion:

```text
POST /api/rooms/:code/arguments/suggest
```

Publish the reviewed structure:

```text
POST /api/rooms/:code/federation/arguments
```

Every public write requires server-side author verification and explicit approval. The private argument suggestion is not a public federation action.

## Argument-map constraints

A signed argument map uses:

```text
nodes: claim | reason | objection | qualification
edges: supports | challenges | qualifies
```

At least one claim is required. Node IDs must be unique. Edge endpoints must exist and differ. Duplicate edges are rejected. The reference validator also enforces:

```text
reason        → supports
objection     → challenges
qualification → qualifies
```

v0.9 permits at most one signed argument map per federated utterance. See `docs/argument-structure.md`.

## Lifecycle semantics

A retraction does not erase the old utterance. It adds a new signed statement that the author no longer endorses it.

A revision links an old utterance to a separately committed and separately federated replacement. Revision chains cannot form cycles.

## Provenance semantics

`cites`, `supports`, and `challenges` are public assertions by the source utterance's author. The system does not infer and publish these edges automatically.

## Persistence

Public federation artifacts are stored separately from ordinary room discourse:

```text
federation_publications  signed utterances
federation_events        signed retractions / revisions
provenance_edges          signed cross-utterance relations
argument_maps             signed intra-utterance structures
```

Raw drafts, clarifications, Intent Cards, AI argument suggestions, and unapproved structures are not stored as public federation state.

## Security scope

The current implementation still avoids inbound federation and arbitrary remote fetching. This postpones SSRF, remote spam, replay handling, cross-instance identity binding, inbound moderation, and delivery retry semantics until those trust boundaries are explicitly designed.
